# Obscura（暗匣）：面向自主代理的密封投标统一价代币发行机制

**技术白皮书 · v0.1 · 2026-08**

---

## 摘要

现有代币发行平台普遍采用先到先得的铸造模式，其分配结果由交易排序能力决定，而非由参与者的真实估值决定。当发行入口从人类界面转向自主代理（AI agent）时，这一缺陷被进一步放大：代理的响应延迟由语言模型推理与工具调用往返构成，天然处于秒级到数十秒级，在 gas 竞价中必然输给专用脚本。

本文提出 Obscura，一个**密封投标、统一清算价的批量拍卖**代币发行机制，并将其唯一投标入口实现为运行在用户本地的 MCP（Model Context Protocol）服务。机制层面，我们通过承诺-揭示消除抢跑、通过统一清算价降低估值猜测博弈、通过有界分批结算使链上 gas 消耗与投标数量解耦。系统层面，我们将资金安全约束下沉至代码强制的三重边界（目标地址冻结、函数白名单、单笔硬上限），使得提示词注入所能造成的最坏后果被限制为一次劣质出价。

我们在以太坊 Sepolia 测试网完成部署与实测，合约测试 19 项通过、行覆盖率 90.24%。本文亦如实报告实测中暴露的三类工程与产品问题：真实网络下的日志分页与交易确认时序缺陷、代理因资金安全护栏而拒绝执行核心工具、以及揭示活性依赖用户在线所导致的真实抵押金损失。

**关键词**：密封投标拍卖 · 统一清算价 · 承诺-揭示 · 自主代理 · MCP · 抗抢跑

---

## 1. 引言

代币公开发行的核心问题是：在供不应求的条件下，如何把有限的供应分配给参与者。

现行主流方案是**先到先得的固定价格铸造**。该方案的分配函数实质上是

> 分配 ∝ 交易被打包的优先级

而交易优先级由 gas 出价与基础设施能力决定。其后果是可预期的：搜索者（searcher）与专用机器人系统性地占据绝大部分份额，普通参与者以失败交易的形式承担成本，而项目方并未因这部分超额支付获得任何收益——它流向了区块生产者。

本文关注的场景更为特殊：**发行入口是用户自己的 AI 代理**。这一设定带来一个额外约束——代理的端到端延迟不可控。若沿用先到先得，机制会自动淘汰代理用户，产品命题自我否定。

因此机制选择不是审美偏好，而是**可行性前提**：必须采用一个**分配结果与时间无关**的机制。

## 2. 设计目标

| 编号 | 目标 | 动机 |
|---|---|---|
| G1 | 分配结果与交易时序无关 | 使代理延迟不构成劣势 |
| G2 | 投标在截止前不可观测 | 消除抢跑与跟单 |
| G3 | 中标者支付同一价格 | 降低估值猜测博弈 |
| G4 | 链上 gas 与投标数解耦 | 保证机制在真实规模下可结算 |
| G5 | 用户私钥不离开本地 | 运营方不成为托管方 |
| G6 | 代理的最坏行为后果有界 | 提示词注入不可导致任意转账 |

## 3. 机制设计

### 3.1 形式化定义

一场拍卖由元组 $\langle S, p_{\min}, T_c, T_r \rangle$ 定义：

- $S$：出售供应量（代币最小单位）
- $p_{\min}$：底价（每 $10^{18}$ 代币单位对应的 wei）
- $T_c$：投标窗口截止时刻
- $T_r$：揭示窗口截止时刻，$T_c < T_r$

参与者 $i$ 提交一份投标 $(p_i, q_i)$，语义为「**最多以单价 $p_i$ 购买至多 $q_i$ 单位**」，即一条在 $p_i$ 处截断的平坦需求曲线。

记已揭示投标集合为 $B$，定义**累积需求函数**

$$D(p) = \sum_{i \in B,\; p_i \geq p} q_i$$

### 3.2 清算价

候选价格集合 $P = \{p_{\min}\} \cup \{p_i : i \in B\}$。清算价定义为

$$
p^* =
\begin{cases}
\max\{\, p \in P : D(p) \geq S \,\} & \text{若 } D(p_{\min}) \geq S \quad (\text{超额认购}) \\[4pt]
p_{\min} & \text{否则} \quad (\text{认购不足})
\end{cases}
$$

**命题 1（可验证性）**：给定候选 $p$，判定其是否为清算价只需一次对 $B$ 的线性扫描，即验证

$$D(p) \geq S \quad \wedge \quad D(p') < S$$

其中 $p'$ 是 $P$ 中大于 $p$ 的最小元素。

这一性质是实现的关键。链上排序需 $O(n^2)$ 或复杂的数据结构，而"链下计算、链上验证"只需 $O(n)$，且提交错误候选值仅导致该笔交易 revert，攻击者除浪费自身 gas 外无所得。

### 3.3 分配规则

记 $D_{>} = D(p')$ 为严格高于清算价的需求，$Q = \sum_{i: p_i = p^*} q_i$ 为恰在清算价的需求，剩余供应 $R = S - D_{>}$。

$$
x_i =
\begin{cases}
q_i & p_i > p^* \quad \text{（全额成交）}\\[4pt]
\left\lfloor \dfrac{q_i \cdot R}{Q} \right\rfloor & p_i = p^* \quad \text{（按比例削减）}\\[4pt]
0 & p_i < p^*
\end{cases}
$$

由清算价的极大性可知 $D_{>} < S$，故 $R > 0$，按比例分配始终良定义。向下取整产生的残余由项目方通过 `reclaimUnsold` 回收。

**所有中标者的支付单价均为 $p^*$**，而非各自的出价。

### 3.4 抵押金与偿付充分性

投标时托管的抵押金为 $c_i = q_i \cdot p_i / 10^{18}$，即按**投标人自己的最高价**计价。

**命题 2（抵押金充分性）**：对任意投标人，$c_i \geq x_i \cdot p^*$，即抵押金恒足额覆盖应付款，退款额 $c_i - x_i p^* \geq 0$。

*证明*：分三种情形。
- $p_i > p^*$：$x_i = q_i$，应付 $q_i p^*$，退款 $q_i(p_i - p^*) > 0$。
- $p_i = p^*$：$x_i \leq q_i$，应付 $x_i p^*$，退款 $(q_i - x_i)p^* \geq 0$。
- $p_i < p^*$：$x_i = 0$，全额退款。 $\square$

该性质使得清算过程无需追加保证金调用，也不存在部分成交后资不抵债的状态。

### 3.5 激励性质与其边界

统一清算价的直觉优势是：**提高出价不改变中标后的支付单价**，因此不存在"报高价即多付"的直接惩罚。

但必须指出一个常被发行方营销文案掩盖的事实：**统一价多单位拍卖并非激励相容的**。

当投标人自身处于边际位置（$p_i = p^*$）时，其出价会影响清算价本身，进而抬高**自己所有中标单位**的支付价。这构成了经典的**需求削减（demand reduction）**激励 [1][2]：理性的大额投标人有动机压低报价或减少申报数量。

其影响强度取决于投标人相对于供应量的规模：

- 当单个投标人的需求远小于供应量时，其对 $p^*$ 的边际影响趋近于零，此时近似真实报价是接近最优的
- 当少数大额投标人主导需求时，削减激励显著

严格的激励相容需要 VCG（Vickrey）式的支付规则，但其链上实现复杂度与 gas 成本远高于统一价，且在实践中存在自身的合谋与预算约束问题。本机制选择统一价，是在**实现可行性、可解释性与激励性质**之间的显式权衡，而非声称其为最优。

### 3.6 承诺-揭示与没收

投标阶段链上仅记录承诺值

$$h_i = \mathrm{keccak256}(\texttt{auctionId} \,\|\, \texttt{bidder} \,\|\, p_i \,\|\, q_i \,\|\, s_i)$$

其中 $s_i$ 为 256 位随机盐值，**仅保存于投标人本地**。

两点设计说明：

**(a) 承诺绑定投标人地址。** 若省略 `bidder` 字段，攻击者可从内存池复制他人承诺并抢先提交，从而窃取其投标内容。

**(b) 盐值不得由运营方持有。** 若运营方掌握盐值，即可提前解开全部密封投标，机制退化为公开报价，G2 失效。这一约束直接决定了架构：**盐值必须存于用户本地，因此投标入口必须运行在用户机器上。**

未在 $T_r$ 前揭示的投标，其抵押金归项目方所有。这并非惩罚性条款，而是必需的：若未揭示无代价，投标人便获得了一个**免费期权**——观察市场后仅在有利时揭示。没收使该期权的行权成本等于抵押金本身。

## 4. 系统架构

### 4.1 信任边界

| 组件 | 持有 | 被信任用于 |
|---|---|---|
| 拍卖合约 | 托管代币与抵押金 | **全部**——唯一事实来源 |
| 本地 MCP 服务 | 用户私钥、投标盐值 | 不对外承担信任；执行本地策略 |
| 元数据 API | 项目方撰写的文案 | **不被信任**，其输出被显式围栏隔离 |
| 看板前端 | 无 | 仅展示 |

关键性质：**投标能力不依赖运营方服务可用性**。元数据 API 不可达时，客户端回退至直接读取链上状态，供应量、底价、窗口、阶段、已揭示需求均不受影响，仅项目方描述降级为不可用。

### 4.2 代理接入层与策略约束

投标入口实现为 MCP 服务，运行于用户机器，由用户的代理宿主（Claude Desktop、OpenClaw、Codex 等）拉起。交易在本地构造与签名，运营方不接触密钥。

所有会改变状态的调用均通过一个策略层，该层强制三重约束：

1. **目标地址**由启动时冻结的配置解析。工具参数中**不存在地址字段**，运行时读取的任何数据（包括项目方文案）均无法影响交易去向
2. **函数**须命中固定白名单。新增合约方法在显式修改白名单前不可达
3. **金额**须不超过用户预设的单笔硬上限，该上限无法从对话内部抬高

**系统中不存在通用转账工具。**

由此可得一个可陈述的安全上界：**提示词注入所能造成的最坏后果是一次劣质出价，其损失以硬上限为界**，而非任意资产转移。

### 4.3 有界结算

结算被拆分为四阶段状态机：

```
submitSettlementBatch  →  finalizeClearing  →  submitAllocationBatch  →  finalizeSettlement
   （降序分批累积需求）      （固定清算价）       （分批计算分配）        （标记完成）
```

链下按价格降序排序后分批提交，合约验证批次间的单调性并累积需求。单笔交易 gas 有界，投标总数不再受区块 gas 上限约束。

`settle` 为**无权限调用**——这既是去中心化属性，也是一项活性风险：无人有义务执行。系统因此需要 keeper 作为兜底基础设施（见 §7.3）。

## 5. 安全分析

### 5.1 抢跑

投标在 $T_c$ 前不可观测，内存池中仅有承诺哈希。承诺绑定 `msg.sender`，无法被复制重放。分配与交易时序无关。**G1、G2 成立。**

### 5.2 提示词注入

`analyze_launch` 会将项目方撰写的文案送入代理上下文，该文案是攻击者可控输入。缓解措施按重要性排序：

1. **不存在可被指使的危险工具**（首要防线）
2. **无工具接受调用方指定的目标地址**
3. **硬上限在签名前强制**
4. **不可信内容以显式围栏包裹**后进入上下文

前三条为代码强制并由自动化测试守护；第四条为纵深防御。**G6 成立**，且上界可精确陈述。

### 5.3 女巫攻击

链上注册表要求质押并按**地址**（而非代理实例）绑定配额。这一区分是必要的：若按代理实例计额，用户启动 N 个代理即可将份额放大 N 倍。

**当前实现的局限**：地址创建成本极低，纯质押不构成充分的女巫防御。合约预留了可插拔的 `IPersonhoodVerifier` 接口，但生产部署必须接入真实的身份证明机制（World ID、Gitcoin Passport 等），或使质押额相对于所解锁份额具有经济意义。

### 5.4 「必须使用自有代理」的不可强制性

必须明确陈述：**该产品规则在密码学上不可强制。**

代理本质上是普通的 MCP/HTTP 客户端。凡代理能发出的请求，脚本亦能发出。MCP 握手中的 `clientInfo` 是客户端自报字符串，可被平凡伪造。不存在 TEE 远程证明、厂商对代理运行时的签名、或任何可证明"此调用来自某代理"的硬件信任根。

因此，代理门槛提供的是**分发渠道与摩擦，而非安全保证**。全部实质性的女巫抵抗位于链上，且与交易的产生方式无关。任何将代理门槛描述为安全属性的表述都是错误的。

## 6. 实现与实测

### 6.1 测试覆盖

| 项 | 结果 |
|---|---|
| 合约单元与随机化测试 | 19 项通过 |
| Solidity 行覆盖率 | 90.24%（语句 91.84%） |
| API / MCP 单元测试 | 8 / 8 通过 |
| MCP 安全断言 | 通过（无通用转账工具、无调用方指定目标） |
| 端到端拍卖数学 | 通过（含超额认购与按比例削减） |

### 6.2 测试网部署观察

系统已部署于以太坊 Sepolia 并完成完整生命周期实测。以下三项问题在本地环境中**均不可复现**，仅在真实网络暴露，具有一般性参考价值：

**(a) 日志查询未分页。** 事件扫描使用 `fromBlock: 0`，在区块数逾千万的公链上被 RPC 提供方以 `exceed maximum block range` 拒绝。本地链仅数百区块，永不触发。修正方案为按块区间分页，并在部署产物中记录起始块高。

**(b) 依赖性交易未等待确认。** 结算状态机严格串行，而 `writeContract` 在交易**提交**时即返回。本地链即时出块掩盖了该缺陷；真实网络上后续步骤在前序交易上链前执行，读到旧状态并以 `SettlementIncomplete` 回滚。

**(c) 打包引入重复守护进程。** 将服务打包为单文件后，被内联模块的"是否为主模块"判断意外成真，导致运行两个揭示循环。根因是库模块含有顶层副作用；修正方案为将 CLI 入口分离为独立文件，并以回归测试断言库模块无自执行代码。

### 6.3 一次真实的抵押金损失

实测中发生了一次非人为设计的失败，其信息价值高于任何设计论证：

一笔投标成功提交后，用户会话结束、客户端关闭；17 小时后揭示窗口过期，**0.05 ETH 抵押金被没收**。

文档中对此风险的书面警告出现过多次，但**警告未能阻止其发生**。这印证了一个一般性判断：**将安全措施实现为需要用户主动启用的可选组件，等价于未实现**。

据此我们将自动揭示守护由独立进程改为**内置于 MCP 服务本身**——代理宿主本就会拉起该进程，守护的边际成本仅为每轮一次合约读取。

其残余局限亦须诚实说明：守护与服务进程共存亡，因而仅在用户的代理宿主运行期间有效。这不是实现缺陷，而是承诺-揭示机制的**固有约束**——在无可信第三方的前提下，投标人必须至少上线一次。

## 7. 局限与后续工作

### 7.1 无释放机制（最显著缺口）

**当前合约不含任何锁仓、悬崖期或线性释放逻辑。** 中标代币在领取时一次性全额交付。

对真实发行而言这是明显缺口：缺少释放约束会使早期抛压不受限制。两条可行路径：

1. 在拍卖合约内实现释放计划，领取时发放凭证而非代币
2. 领取时将代币转入独立的 vesting 合约

**倾向方案 2。** 拍卖合约的审计面已因分批结算状态机而显著扩大，将释放逻辑耦合进来会进一步增加关键路径的复杂度；职责分离亦使 vesting 合约可独立审计与复用。

### 7.2 女巫抵抗

见 §5.3。生产部署前必须接入身份证明或提高质押的经济意义。

### 7.3 结算与揭示的活性

`settle` 与揭示均无权限亦无义务人。前者需要 keeper 基础设施；后者依赖投标人上线。可能的改进方向包括：

- 对执行结算者给予协议内激励
- 引入门限加密或时间锁加密，由委员会或 VDF 在截止后解密投标，从而消除对投标人回访的依赖

后者可根本性地解决 §6.3 所述问题，但会引入委员会假设或新的密码学依赖，属重大机制变更。

### 7.4 审计状态

**本系统未经任何外部安全审计。** Slither 与 Mythril 因环境依赖未执行。当前仅适用于测试网。

## 8. 结论

本文提出的机制以一个约束为出发点：当发行入口是延迟不可控的自主代理时，任何依赖交易时序的分配方式都不可行。密封投标统一价批量拍卖将时间维度从竞争中移除，从而使代理参与成为可能——**机制选择与产品形态互为前提**。

在安全侧，我们主张一种可陈述的立场：与其宣称代理不会被诱导，不如**使其被诱导后的最坏后果有界**。目标地址冻结、函数白名单与单笔硬上限三者共同将攻击面收敛至"一次劣质出价"。

我们同时明确否定一个易被误用的营销表述：「必须使用自有代理」不具备密码学强制力，其价值在于分发与摩擦，全部实质安全性位于链上。
